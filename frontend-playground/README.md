# frontend-playground

Статическая копия веб-морды `server/public/` для дизайна и новых идей.
**Бэкенда нет:** `mock-api.js` подменяет `window.fetch` и отвечает на
`/api/*` из памяти браузера. Реальные файлы не качаются, реальная БД не
трогается, настоящий `server/public/` не меняется.

## Запуск

```bash
cd frontend-playground
node serve.mjs
# открыть http://127.0.0.1:4173/
```

`serve.mjs` — только статическая раздача файлов, не API. Никаких `npm install`
и `node src/index.js` не нужно. Можно и без него:

```bash
cd frontend-playground
python3 -m http.server 4173
```

Можно открыть и просто `index.html` файлом — `fetch` уже перехвачен, сеть не
нужна. Но статический сервер удобнее: одинаково работает в Chrome/Firefox и
не упирается в ограничения `file://` на `localStorage`.

## Что внутри

| Файл | Зачем |
|---|---|
| `index.html` | копия реальной страницы + подключение `mock-api.js` / `playground-ui.js` |
| `app.js` | копия реального фронтенда; здесь меняются экраны и поведение |
| `styles.css` | копия реальных стилей; здесь меняется дизайн |
| `mock-api.js` | демо-API: очередь, история, Mango, настройки, сценарии |
| `playground-ui.js` | плавающая панель с кнопками сброса/сценариев |
| `playground.css` | стили только для панели; не попадают в боевой UI |

## Панель

В правом нижнем углу — `PLAYGROUND`:

- **MangaLib: том 6 — 12, том 7 — 8** — тот самый перекос: 61 и 62 лежат в
  шестом томе, хотя по MangaDex они должны быть в седьмом.
- **MangaDex: том 6 — 10, том 7 — 10** — правильная раскладка для сравнения.
- **Перенести 61–62 в том 7** — быстрый сценарий; ниже есть и ручной редактор.
- **+ задача** — добавляет ещё одну задачу в очередь.
- **+ прогресс** — сдвигает демо-загрузку на 5 секунд.
- **Сброс** (или `Alt+R`) — возвращает исходные примеры.

Состояние хранится в `localStorage` под ключом `idk-playground-v1`, поэтому
переживает перезагрузку страницы. Сброс очищает только это состояние.

## Что уже есть в примерах

- **Queue**: фильм, сериал с видео и субтитрами, ошибка 403, пауза,
  отменённая задача; прогресс и скорости двигаются сами.
- **Mango**: два задания (одно качается, одно готово), история глав,
  выбор томов/глав, удаление тома.
- **History / Mango**: тома спрятаны под заголовком `Volumes · N chapters`;
  по умолчанию свёрнуто, заголовок раскрывает список.
- **Редактор томов**: кнопка `Edit volumes` у выбранного тайтла, у задания и у
  скачанной истории. Выбираешь главы и любой том — существующий или новый
  (например, 1 или 2); крайние главы едут вместе, чтобы в томе не было
  пропусков. Можно собрать все главы в один том и разложить заново.
  У задания режим сначала ставит его на паузу, после переноса возобновляет.
  Файлы в прототипе имитируются.
- **Mango → языки**: у MangaDex-сценария есть чипы `RU` / `EN`; у MangaLib
  чипов нет — он всегда русский.
- **Settings**: форма заполнена, сохранение работает в памяти/localStorage;
  переключатель языка теперь только здесь (кнопки EN/RU в сайдбаре убраны).
- **Name template: mango** — отдельный шаблон с предпросмотром:
  `%orig_title%%year_part%/Volume %volume%/%chapter%%chapter_title_part%`.
- **History → Files**: вместо сухой таблицы — карточки по фильмам/сериалам,
  как в Mango, со списком файлов и действиями.
- **Categories**: редактор правил «раздел + тип + рейтинг → папка». В примерах
  уже есть морковные/арбузные/банановые/томатные папки; 16+ и 18+ у мультфильмов
  уходят в томатные, а не в общие мультики. Raw legacy-маппинг убран;
  папки создаются сразу внутри Download folder, отдельной Library folder нет.
  Логика определения типа — в [`PORTING.md`](PORTING.md).
- **Rezka cookies**: поле для Netscape-экспорта, счётчик распознанных cookies.
  В прототипе никуда не отправляется и в репозиторий не пишется.
- **Add by link**: вставил ссылку → «Разобрать» → карточки на каждый фильм/
  сериал. В каждой карточке качество, озвучка, серии (для сериалов), «Скачать
  заново» и автоматические субтитры. Без «Скачать заново» уже скачанное
  пропускается; с ней — перекачивается. Referer-поля нет: источник берётся из
  ссылки.

## Как пробовать новое

1. Меняй `styles.css` — цвета, отступы, типографику.
2. Меняй `app.js` — разметку и обработчики. Это обычный vanilla JS, без сборки.
3. Добавляй данные/эндпоинты в `mock-api.js`. Все ответы — обычный JSON:
   удобно проверять новые экраны без сервера.
4. Если добавляешь новую вкладку (например, музыку): добавь пункт в
   `index.html`, секцию `.view`, маршрут в `currentRoute()`/`applyRoute()` и
   мок-эндпоинт в `mock-api.js`.

Когда дизайн готов — переноси изменения в `server/public/` вручную (или
`diff -u` и применяй патчи). Это сознательная копия, а не второй боевой
фронтенд: чтобы не было соблазна «поправить только playground».

Что именно переносить в бэкенд/фронтенд, с API, файловыми операциями и
порядком шагов — в [`PORTING.md`](PORTING.md).

## Ограничения

- Нет реальных сетевых запросов, файлов, ffmpeg, БД и Chromium.
- Перенос глав меняет только демо-модель. В боевом бэкенде понадобится
  эндпоинт, который переименовывает папки/`.idk-part` и обновляет
  `mango_chapters.volume` — это ещё не сделано.
- Cookies и франшизы/закладки — только макет: resolver и загрузка по cookie
  не реализованы. Поле считает строки Netscape и хранит текст в localStorage;
  в репозиторий куки не попадают.
- Конструктор Categories и `library_rules` — тоже макет: боевой сервер пока
  читает старый `library_categories` (`section = folder`). Для 16+/18+ нужна
  миграция настроек и поддержка рейтинга в сортировке.
- `fetch` перехватывается только для путей `/api/*`; остальное уходит в
  обычный браузерный `fetch` (в статической копии ничего не запрашивается).
- Ошибки сервера эмулируются только там, где это нужно для примеров
  (403 у Интерстеллара, платные главы — можно добавить по аналогии).
- Скриншоты/анимации не сохраняются; для сравнения версий используй git.
