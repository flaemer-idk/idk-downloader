# Mango: дизайн (com-x.life первым, MangaDex потом)

> **Актуальная версия — [`../../mango.md`](../../mango.md).** Этот файл —
> исторический прототип дизайна (правила папок и первые живые проверки);
> свежие решения по MangaDex/MangaLib и статус — в корневом `mango.md`.
>
> Рабочий документ по дизайну манго-качалки. Факты про сайт и обзор готовых
> качалок — в [research.md](./research.md), прототип UI — [prototype.html](./prototype.html).
> **Дизайн реализован в сервере:** `server/src/mango/` (адаптер, headless
> Chromium, очередь), вкладка «Манга» в веб-морде, история в БД. Этот файл —
> источник правил и объяснений, а не план «на потом».

## Принципы

1. **Меньше вопросов юзеру при добавлении.** Юзер качает пачками, а не по одной
   главе. Никаких «выберите обложку», «подтвердите название», «выберите формат».
   Нажал «скачать главы» — всё уехало в очередь.
2. **Программа не трогает содержимое после скачивания.** Юзер всё равно правит
   результат руками: удаляет страницы с рекламой переводчика/спойлерами (они
   бывают в начале, середине и конце с разным количеством — автоматически это
   не заметить, а vision-модель дорогая и с overhead). Значит, downloader просто
   кладёт страницы как есть и никогда не перепроверяет и не дописывает в готовые
   папки.
3. **Никаких служебных файлов рядом с контентом.** Ни `.complete`-маркеров, ни
   `ComicInfo.xml`, ни кэша внутри папок тайтла. Служебное состояние (что
   скачано, откуда, что пропущено) — в БД сервера.
4. **Обложку качает не программа, а юзер.** На сайтах обложки часто всратые
   (144p), а нормальную находишь на wayback machine или где ещё, потому что
   тайтл непопулярный. Юзер сам кладёт `Cover.png` в папку тайтла — до, после
   или между скачиваниями глав, программе всё равно.

## Структура папок

```
{Название} [{год}]/
├── Cover.png                  ← кладёт юзер, программа не проверяет
├── Volume 1/
│   ├── 8 - яблоко зеленое сорванное название/
│   │   ├── 000.png            ← нумерация с 000, расширение оригинала
│   │   ├── 001.jpg
│   │   └── 002.jpg
│   └── 2.5 - Экстра/
│       └── 000.png
└── Volume 2/
    └── 12/                    ← у главы нет названия → папка без названия
        └── 000.png
```

`{Название}` — всегда **русское** (`h1.flex-grow-1`): оно на ComX есть всегда,
в отличие от английского (`h2.page__title-original` — бывает не всегда).
Английское и альтернативные названия (`page__alt-names`) не используем вообще —
незачем. Год — из инфоблока (`Год: <a>2020</a>`); года нет → папка просто
`{Название}` без скобок.

### Папка главы: разбор строки с сайта

Разделитель тома и главы на ComX — `« - »` **с пробелами** (`1 - 8` = том 1,
глава 8):

| строка на сайте           | папка                                  |
|---------------------------|----------------------------------------|
| `1 - 8`                   | `Volume 1/8`                           |
| `1 - 2.5 Экстра`          | `Volume 1/2.5 - Экстра`                |
| `1 - 5 5 лет спустя`      | `Volume 1/5 - 5 лет спустя`            |
| `1 Кому улыбнётся мир?`   | `Volume 1/1 - Кому улыбнётся мир?`     |

- До первого `« - »` — том; после — номер главы (старшая числовая часть с
  точками) и опциональный хвост-название.
- **Главы без тома** (у оншотов строка вида `1 Название`, разделителя нет):
  номер = вся числовая часть, название = хвост. Кладём в `Volume 1/` — структуру
  держим однородной. Поле «Тип выпуска: Ван-шот» на сайте есть не у всех оншотов,
  на него не полагаемся. Случай редкий: почти у всех есть хотя бы `1 - 1`.
- Названия у главы нет → папка называется просто номером, без дефиса.
- Строки номера вида `8-9` (если вдруг встретятся — две главы в одном выпуске)
  трактуем буквально: папка `8-9`.
- Название главы и `{Название}` тайтла проходят санитизацию: `/ \ : * ? " < > |`
  и управляющие символы → `_`, хвостовые точки/пробелы срезаются
  (Windows-совместимость — папка может уехать на NAS/ТВ), лимит ~150 символов.
- Номер главы нулями не дополняем (`8`, а не `008`) — сортировку держит
  натуральная сортировка проводников.

### Файлы страниц

- `{номер с 000}.{расширение из Content-Type}`: `000.png`, `001.jpg`,
  `002.webp`. **Ничего не перекодируем** — кладём ровно то, что отдал сайт.
- Расширение берём из фактического `Content-Type` ответа, а **не из URL**: CDN
  ComX перекодирует всё в WebP (проверено 2026-10-26: URL с `.jpg` отдаёт
  `image/webp`, magic bytes — `RIFF…WEBP`). Оставить `.jpg` у webp-байтов —
  грязно, часть читалок спотыкается.
- Добиваем нулями до 3 цифр; если страниц ≥ 1000 — до 4 (количество страниц
  известно из `__DATA__` до скачивания).
- Порядок страниц — как в `__DATA__` сайта, нумеруем по индексу.

## Повторное добавление и дубли

Два разных случая:

1. **Тот же тайтл добавляют снова** (по ссылке на ту же страницу). Определяем
   по источнику (URL страницы) в БД, а не по названию. Логика:
   - в БД хранится, какие главы этого тайтла уже скачаны (том, номер, название,
     количество страниц);
   - при новой пачке главы, которые уже есть в истории, **молча пропускаются**;
     недостающие — качаются;
   - если качать нечего (всё выбранное уже скачано) — предупреждение в UI
     «всё уже скачано», ничего не ставим в очередь. Юзер может повторно
     принудительно — но по умолчанию нет;
   - на уровне файловой системы правило остаётся прежним: **папка главы
     существует = глава полная** (юзер мог удалить страницы — его контент, не
     перепроверяем). БД — для подсчёта/предупреждений, диск — истина в последней
     инстанции.
2. **Другой тайтл с совпадающим именем+годом** (коллизия имени папки).
   Создаём рядом с номером-суффиксом: `Название [2020] 2`, потом `3` и т.д.
   (первый свободный номер).

## Откуда данные (ComX)

Рецепт из research.md, отработанный в трёх чужих реализациях:

- Сайт на DLE с антиботом DleGuard: первый запрос редиректит на `/_c?t=...`,
  после JS-челленджа ставится cookie `__guard_trust`. Публичного API нет.
- Список глав и пути картинок лежат в JSON-блобе `window.__DATA__` на страницах.
- Картинки: `https://{host}/comix/{path}`, host из `__DATA__`:
  `img.com-x.life` (глобально) или `rus.com-x.life` (для РФ). Хост выбирать по
  полю `hostRu` из `__DATA__`, а не хардкодом.
- Референсы по эндпоинтам и краевым случаям: `ComX.kt` из Keiyoushi
  (`src/ru/comx`) и форк Forsash3451k/comx-downloader (активен, 09.2026).
- Rate limit: ~3 запроса/сек (как у Keiyoushi), картинки качать с `Referer` на
  страницу тайтла.

## Архитектура: модульность источников

Источники (ComX сейчас, MangaDex потом) — **плагины-адаптеры** поверх общего
пайплайна. Общая часть ничего не знает про HTML/API конкретного сайта:

- **адаптер источника** — маленький модуль с контрактом:
  - «дай инфо о тайтле по ссылке» → `{название, год, главы[]}` (каждая глава:
    том, номер, название, ссылка/ключ на адаптер);
  - «дай список ссылок на страницы главы» → `[url...]`;
  - «скачай страницу» (если источнику нужны свои заголовки/cookies — тут);
  - опционально «поиск».
- **общий пайплайн** — очередь, раскладка по папкам `{Название} [{год}] /
  Volume N / глава / 000.png`, нумерация, ретраи, `.idk-part`-переименование,
  история в БД, предупреждения при повторе.

MangaDex потом = новый адаптер (официальный API, `translatedLanguage[]`,
at-home), пайплайн и папки те же. Переписывать ничего не надо.

### Обход DleGuard: серверный headless Chromium (проверено) + расширение (запасной путь)

**Основной путь — без клиента вообще** (проверено 2026-10-27, `headless-test.mjs`):
сервер запускает безголовый системный Chromium через `puppeteer-core` (не
Selenium: никаких драйверов/Java, тонкий клиент к готовому браузеру):

1. Юзер вставляет ссылку на тайтл в веб-морду (хоть с телевизора, клиент не
   обязан когда-либо открывать com-x.life) → «скачать».
2. Сервер запускает headless Chromium (только на момент добавления тайтла, не
   во время скачивания), открывает страницу тайтла. DleGuard-челлендж решается
   сам при загрузке — **без логина и cookies**.
3. Из `window.__DATA__` — название, год, главы; страницы читалки — так же.
4. Браузер закрывается, картинки качаются обычным fetch (хост картинок DleGuard
   не охраняет, см. выше).

Ключевые детали из теста:
- обязательно скрыть `navigator.webdriver` (`--disable-blink-features=AutomationControlled`
  + подмена свойства) — иначе DleGuard тарпитит страницу;
- Chromium — системный бинарник (`puppeteer-core` ничего не качает сам);
  в NixOS-модуле добавить `chromium` в пакеты сервиса;
- профиль браузера держать (`userDataDir`): сессия DleGuard переживает перезапуски,
  повторные добавления ходят без челленджа.

Это гонка щитов: если DleGuard однажды начнёт палить headless — **запасной путь
уже готов и отработан** (расширение достаёт данные из вкладки юзера, как у
hdrezka). Оба пути складываются в один контракт адаптера: «инфо тайтла + данные
читалки», откуда они взялись — детали.

> **Хосты картинок — проверено живыми запросами 2026-10-26, cookies НЕ нужны.**
> Обе картинки юзера (обложка `/uploads/posts/...` и страница главы
> `/comix/26588/918139/...jpg`) отдаются с кодом 200 без `__guard_trust` —
> DleGuard охраняет только HTML-страницы, а их и так достаёт расширение.
> Условия:
> - обязательны браузерные заголовки: реальный User-Agent + `Accept: image/...`
>   как у Chrome + `Referer` на страницу тайтла;
> - без `Accept` (или с голым curl) `rus.com-x.life` **молча подвешивает**
>   запрос до таймаута — не отказ, а тишина; с полными заголовками отвечает
>   нормально;
> - `img.com-x.life` (за Cloudflare) отвечал стабильно, `rus.com-x.life` —
>   после первого таймаута тоже. В адаптере качаем через `img.com-x.life`,
>   а `rus` — запасной вариант (хост всё равно приходит из `__DATA__`, не
>   хардкодим).

> **HTML-страницы сервером не читаются вообще — проверено 2026-10-27.**
> Страница тайтла и читалки с сервера не грузятся никак: сначала DleGuard
> редиректит на `/_c?t=...` (тикет в base64 содержит IP юзера), потом запросы
> **молча тарпитятся по таймауту** — даже с реальными cookies юзера
> (`dle_user_id`/`dle_password`/`PHPSESSID`) и полным набором заголовков Chrome.
> Похоже на отпечаток TLS: curl и Node-fetch палятся, лечится только настоящим
> браузером (в реальном браузере DleGuard проходит сам, даже без логина).
> Выводы:
> - **cloudscraper/Selenium не спасли бы без TLS-мимикрии** — в референсе
>   Selenium используется только как одноразовый помощник логина ради cookies;
> - идея «юзер вставляет cookies в настройки» для HTML не работает и не нужна:
>   данные страниц берёт **расширение из браузера юзера** (прототип отработал
>   эту схему: JSON с инфо тайтла и читалки → сервер качает картинки);
> - сервер делает только то, что ему по силам: скачивание картинок.

## Куда сохранять

Отдельный конфиг **`MANGO_DIR`** — корень манго-библиотеки, задаётся в
настройках сервера (по умолчанию — подпапка внутри стандартного `saveDir`:
медиатека, если настроена, иначе папка загрузок).

## Проверки на живом сайте (аккуратно)

- curl'ом сайт может «врать»: DleGuard на любой запрос отдаёт страницу проверки
  вместо контента, а CDN режет по User-Agent. Проверять нужно **код ответа и
  содержимое страницы**, а не только статус; ставить реальный браузерный
  User-Agent (тот же, что у расширения/обычного Chrome), держать rate limit
  ~3 запроса/сек, не долбить.
- Эталон логики — `ComX.kt` из Keiyoushi и форк Forsash3451k: их рецепты
  проверены на живом сайте, с ними сверяться вместо угадывания.

## Что сознательно НЕ делаем

- Не качаем обложку, не пишем `ComicInfo.xml`, не пишем метаданные в папки
  (принципы 3 и 4).
- Не CBZ/CBR — юзеру нужны живые папки.
- Не фильтруем рекламные страницы — принцип 2.
- Не переименовываем/не дописываем ничего в уже скачанные главы.
- MangaDex — позже, как новый адаптер (см. «Модульность источников»).

## Прототип (рабочий, чистый Node без зависимостей)

В этой папке лежит проверенный на живом сайте прототип:

- `comx.mjs` — адаптер ComX: cookies в Netscape-формате, `window.__DATA__`,
  правила имён (`parseChapterString`, `sanitizeName`), скачивание картинок с
  перебором хостов и ретраями;
- `download.mjs` — пайплайн: `{Название} [{год}]/Volume N/глава/000.ext`,
  `.idk-part` до готовности, скип существующих папок, выбор глав `--chapters
  1,2.5,8-10`;
- `info-26588.json`, `reader-918139.json` — образцы данных «как отдаст
  расширение» (вынуты из браузера): инфо тайтла + страницы главы 1-1;
- `cookies*.txt` — в gitignore, не коммитить.

Живой тест 2026-10-27: глава `1 - 1` «Суи и Нери с закатной планеты [2020]» —
27 страниц скачаны в `out/Суи и Нери с закатной планеты [2020]/Volume 1/1/`
(`000.webp`…`026.webp`, настоящие WebP 1200×1707), повторный запуск — «уже
есть», глава без данных читалки — понятный провал без мусора на диске.

```bash
node prototypes/mango/download.mjs "https://com-x.life/26588-sui-i-neri-s-zakatnoj-planety.html" \
  --info prototypes/mango/info-26588.json --chapters 1
```
