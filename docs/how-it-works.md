# Как всё работает: от клика в браузере до файла на диске

Это главный документ «разжевывания». Он идёт по всей цепочке шаг за шагом и
объясняет, **зачем** каждый шаг нужен, а не только что в нём происходит.
Справочные подробности (колонки БД, все эндпоинты, все настройки) — в соседних
доках: [`server.md`](server.md) и [`extension.md`](extension.md).

---

## 0. Роли участников — кто что умеет

Прежде чем идти по цепочке, зафиксируем разделение труда. Оно объясняет почти
все архитектурные решения.

| | Расширение (браузер) | Сервер (Node.js) |
|---|---|---|
| Открывает страницы сайта | ✅ да — через ваш браузер | ❌ никогда — сайт отдаёт ему антибот-страницу |
| Общается с сайтом | ✅ из контекста страницы, с вашими куками | ❌ (к CDN — только качать файлы) |
| Знает очередь и историю | ❌ только текущие задачи в попапе | ✅ SQLite — единственный источник правды |
| Качает файлы | ❌ только отправляет ссылки | ✅ Range-докачка, паузы, повторы, HLS |
| Держит настройки | только адрес сервера + токен | все настройки очереди/имён/медиатеки |

Ключевое следствие: **сервер никогда не ходит на сам сайт**. Он только качает
файлы с CDN по ссылкам, которые принёс клиент. Поэтому у него нет сессии, и
протухшую ссылку он сам перерезолвить не может (об этом ниже).

---

## 1. Полный путь задачи — 8 шагов

```
 [1] Открываете страницу фильма на hdrezka
 [2] Расширение определяет страницу (фильм/сериал) и читает плеер
 [3] Расширение выпрашивает прямые ссылки у сайта (из контекста страницы)
 [4] Расширение пробует качества (вес + реальное разрешение)
 [5] Вы жмёте «Скачать на сервер» → задачи уходят POST /api/tasks
 [6] Сервер кладёт их в SQLite-очередь и валидирует
 [7] Воркеры качают: HTTP GET + Range, докачка, повторы; HLS — через ffmpeg
 [8] Файл готов: переименовывается по шаблону, ложится в медиатеку
```

### Шаг 1–2. Определение страницы и чтение плеера

Когда вы открываете попап расширения, он инъектирует маленькую функцию в
контекст страницы (MAIN world) и та смотрит:

- **HTML страницы**: разметка hdrezka (`/films/`, `/series/`, `/animation/` в
  URL — это будущая категория для медиатеки; `.b-translator__item` — список
  озвучек; названия в `.b-post__title`).
- **Конфиг плеера**: в HTML страницы есть вызов вида
  `sof.tv.initCDNSeriesEvents(1234, 567, 89, false, ...)` — это «паспорт»
  текущего эпизода: id фильма, id перевода, сезон, серия, `favs` (антибот-токен
  сайта), флаги camrip/ads/director. Расширение парсит этот вызов **как
  настоящий JS-вызов** (устойчиво к перестановке аргументов на разных зеркалах).

Подробности парсинга — [`extension.md`](extension.md#1-определение-страницы).

### Шаг 3. Получение прямых ссылок (резолв)

В оригинальном (старом) расширении запросы к сайту шла из service worker с
подменой заголовков через `declarativeNetRequest` и фолбэком «через страницу»
для Cloudflare. Здесь всё проще и надёжнее: **запрос делается прямо из
контекста страницы** (MAIN world).

Что это даёт:

- запрос несёт **куки вашего браузера** — сайт видит обычного залогиненного
  пользователя, как будто вы переключили озвучку в плеере;
- Referer/Origin проставляет сама страница — подменять заголовки не нужно;
- **Cloudflare не мешает**: если сессия уже пройдена в браузере, она действует и
  на этот запрос.

Технически запрос — POST на `/ajax/get_cdn_series/` с телом вида
`id=…&translator_id=…&season=…&episode=…&favs=…` (для фильма — `action=get_movie`,
для серии — `action=get_stream`). Ответ — JSON со строкой качеств:

```
[1080p]https://cdn…/file1.mp4 or https://cdn…/file2.mp4,[720p]https://cdn…/file3.mp4
```

Расширение разбирает эту строку (`decodeVideoURL`) в список качеств, где у
каждого качества — **несколько зеркал** («or»): первое станет основным URL,
остальные — резервными (`alt_urls`), сервер переключится сам, если основное
не отвечает.

Субтитры приходят в том же ответе отдельной строкой (`[Русский]https://…vtt`)
плюс `subtitle_lns` — коды языков от сайта (важно для имён файлов).

### Шаг 4. Проба качеств

hdrezka врёт в подписях: «1080p» может оказаться 720p. Поэтому расширение для
каждого качества **720p и выше** делает Range-запрос на первые 128 КБ файла:

- из `Content-Range` достаёт полный вес файла;
- из шапки MP4 (боксы до `moov` → `stsd`) — реальное разрешение и кодек;
- для `.m3u8` — RESOLUTION/BANDWIDTH из мастер-плейлиста (вес получается
  прикидочный: битрейт × длительность).

Результат показывается прямо в списке качеств: `1080p [720p] 1.1 GB` — оранжевая
подкоробка значит «внутри меньше, чем обещано». Ниже 720p пробы нет вовсе — это
мусорные качества, а каждая проба это лишний запрос к CDN. Результаты кэшируются
на 12 часов по самой ссылке (ссылки hdrezka подписаны и после перезагрузки
страницы меняются — кэш честно промахивается, и проба идёт заново).

Проба — единственное место, где расширению нужен `declarativeNetRequest`:
`Referer` нельзя поставить через `fetch` (запрещённый заголовок), поэтому на
время запроса ставится временное DNR-правило и снимается после ответа.

### Шаг 5. Отправка задач

Вы жмёте «Скачать на сервер». Расширение:

1. Разворачивает выбор в список задач: фильм = 1–2 задачи (видео + субтитр);
   сериал = 2 × число серий. Для сериалов это не мгновенно: **сбор ссылок идёт
   по сериям на вкладке страницы** (по одному запросу на серию, пауза 0.35 c),
   поэтому цикл живёт в самой странице (`window.__idkJob`), а попап можно
   закрыть — он потом подхватит прогресс.
2. Проверяет место: вес из пробы × число серий против `needBytes` сервера.
   Не влезает → первый клик только предупреждает, кнопка становится
   «Всё равно скачать».
3. Шлёт `POST /api/tasks` — массив объектов вида:

```json
{
  "url": "https://cdn…/file.mp4",
  "alt_urls": ["https://cdn…/mirror.mp4"],
  "referer": "https://hdrezka…/series/…",
  "movie_id": "1234",
  "title": "Моб Сити",
  "orig_title": "Mob City",
  "quality": "1080p",
  "voiceover": "Дубляж",
  "season": "1", "season_title": "1 сезон",
  "episode": "2", "episode_title": "Название серии",
  "year": "2013",
  "category": "series",
  "file_type": "video",
  "total_bytes": 1173402624,
  "real_width": 1280, "real_height": 720
}
```

Обратите внимание: `filename` не передаётся — **имя файла собирает сервер по
своим шаблонам** (шаг 6). А вот `referer` критичен: без него CDN часто отвечает
403, и это же — «ссылка на страницу-источник» для протухших ссылок.

### Шаг 6. Сервер принимает задачи (`prepareTask`)

Сервер валидирует и приводит каждую задачу к строке БД:

- URL обязан быть `http(s)://` и вести на файл; `file_type` определяется из
  поля клиента, а если его нет — по расширению ссылки (`.vtt` → субтитры);
- все поля принимаются в двух вариантах (`movie_id` и `movieId`) — клиентам
  удобно;
- если `filename` не передан, сервер **строит имя по шаблону** из настроек.
  Для фильма: `%orig_title%%year_part%/%orig_title%` →
  `Mob City (2013)/Mob City.mp4`. `%orig_title%` — это «лучшее название»:
  из вариантов через « / » выбирается английский, иначе оригинальное, иначе
  русское. Слэши внутри названий (`AC/DC`) подпапок не создают — всё
  санитайзится;
- медиатека: если настроена, сверху добавляется папка категории
  (`category = series` → `Сериалы/…`) — раскладку (`films = Банановые фильмы`)
  задаёте вы в настройках.

Задачи вставляются в SQLite (таблица `tasks`), и в ответе сразу возвращается
свежий расчёт места уже **вместе с новыми задачами** — чтобы предупредить о
нехватке места сразу, а не посреди сериала.

### Шаг 7. Воркеры качают

Пул воркеров просыпается каждые 500 мс и атомарно «отщипывает» задачи из
очереди (`UPDATE … WHERE id = (SELECT … LIMIT 1) RETURNING *` — двойного старта
не бывает даже при нескольких воркерах). Параллельно качается
`max_concurrent` файлов (по умолчанию 2, максимум 16).

Про одно скачивание:

1. Файл пишется во временный `Фильм.mp4.<id-задачи>.part` — id в имени нужен,
   чтобы две загрузки с одинаковым именем не затирали `.part` друг друга.
   Если найден старый `.part` от прежних версий сервера — он подхватывается.
2. Обычный HTTP GET **на core-модулях Node** (`node:http`), не на `fetch`.
   Это осознанный костыль: у undici есть баг, при котором пауза потока из-за
   медленного диска + обрыв соединения роняют весь процесс. llhttp такое
   переживает. Редиректы (301/302/303/307/308, до 5 штук) разбираются руками.
3. Заголовки: `User-Agent` (из настроек, по умолчанию — Chrome), `Referer` из
   задачи, `Accept-Encoding: identity` (иначе сжатие сломает размер).
4. Если `.part` уже существует — докачка: `Range: bytes=<размер>-`. Ответ 206 →
   пишем в конец файла, 200 → сервер Range не понял, начинаем заново.
5. Прогресс пишется в БД не чаще раза в 500 мс (чтобы не изнашивать SQLite).
   Итог проверяется: если получили не столько байт, сколько обещал
   `Content-Range` — это ошибка, задача пойдёт на повтор.
6. Несколько зеркал (`alt_urls`): основной URL не подошёл → пробуется
   следующий, докачка при этом начинается с того, что успело скачаться.
7. Ошибка → повтор с нарастающей задержкой (`retry_delay_ms × номер попытки`,
   максимум 5 минут), до `max_attempts` раз. После — статус `error`, задачу
   можно вернуть кнопкой «Повторить».
8. Пауза/отмена: у каждой активной загрузки есть `AbortController` и «режим»
   (`run`/`pause`/`cancel`). Обрыв по паузе → статус `paused`, `.part`
   сохраняется; по отмене → `canceled`, `.part` удаляется.

**HLS (`.m3u8`)** — отдельная ветка: это не файл, а плейлист из сотен кусочков.
Сервер отдаёт его `ffmpeg` (`-c copy`, склейка без перекодирования) с теми же
Referer/UA, прогресс снимается по размеру временного файла. ffmpeg не
установлен → задача сразу падает с понятной ошибкой.

### Шаг 8. Готово

`.part` переименовывается в финальное имя. Перезапись безопасна: если настройка
«перезаписывать» включена, старый файл заменяется только после полной загрузки
нового (rename в конце) — обрыв посреди загрузки старый файл не трогает. Если
перезапись выключена — подбирается свободное имя `Фильм (1).mp4`.

В БД пишутся финальный размер и путь. Веб-морда (опрос раз в секунду) и попап
(раз в 3 секунды) показывают «готово».

## 2. Как на самом деле выглядит скачивание сериала

Конкретика вместо абстракции. «Mob City», 2 сезона, 20 серий:

1. Открыли страницу серии 1, открыли попап. Расширение определило `SERIAL`,
   вытянуло id перевода и `favs`.
2. Выбрано «Весь сериал» (по умолчанию). Расширение запросило список сезонов
   (`get_episodes`) и показывает «К отправке: 20 серий (2 сезона)».
3. «Скачать» → на вкладке запускается цикл `pageCollectLinks`: для каждой серии
   POST `get_stream` → строка качеств → выбрано качество 1080p Ultra → ссылки
   в очередь заданий. Между сериями 0.35 c. Попап показывает «Собираем ссылки:
   7 из 20» и **может быть закрыт** — цикл живёт в странице.
4. Когда все серии собрались — одним-двумя `POST /api/tasks` уходят 40 задач
   (20 видео + 20 субтитров, если русские есть).
5. Сервер качает по 2 файла параллельно. Попап закрыт, браузер выключен —
   неважно. Веб-морда показывает: `Mob City (2013)` → `Season 1` → карточки
   серий, внутри — видео и субтитры с индивидуальным прогрессом.
6. Итог на диске:

```
<медиатека>/Сериалы/Mob City (2013)/Season 1/Mob City S1E1.mp4
<медиатека>/Сериалы/Mob City (2013)/Season 1/Mob City S1E1.rus.vtt
<медиатека>/Сериалы/Mob City (2013)/Season 1/Mob City S1E2.mp4
…
```

Такую раскладку Jellyfin подхватывает без настройки: год — только на папке,
сезоны — в подпапке `Season N`, субтитр называется как видео + код языка.

## 3. Сценарии «что если»

### Ссылка протухла (задача с ошибкой 403/404)

Ссылки hdrezka подписаны по времени и живут часами. Если очередь долго стояла,
задачи начнут падать. Сервер **не может** взять свежую ссылку — у него нет
сессии сайта. Решение у каждой задачи есть `referer` — адрес страницы:
- имя задачи в очереди/истории и в попапе — ссылка на страницу-источник;
- у сбойной задачи с ошибкой 4xx появляется подсказка: открыть страницу →
  «Скачать на сервер» снова → уйдут задачи с **свежими** ссылками.

Повторная загрузка не плодит мусор: при включённой перезаписи файлы заменяются.

### Рестарт сервера посреди загрузки

При старте сервер находит задачи в статусе `downloading` и возвращает их в
очередь (`queued`) с логом «докачаются с места обрыва». Воркер находит тот же
`.part` (в нём id задачи) и продолжает с `Range: bytes=…`.

### «Уже скачивалось»

Открываете попап на странице, которую уже качали — расширение спрашивает у
сервера `GET /api/movies/:movieId` (сводка: сколько готово/качается/на диске) и
показывает предупреждение: «Повторная загрузка перезапишет готовые файлы». Там
же кнопка **«Отменить этот фильм»** — отменяет незаконченные задачи именно
этого фильма (`POST /api/movies/:movieId/cancel`), не трогая чужие.

### Кончилось место

- **До отправки**: расширение оценивает партию (вес из пробы × серии) против
  `needBytes`. Не влезает → подтверждение вторым кликом.
- **После отправки**: сервер пересчитывает место уже с новыми задачами; веб-морда
  держит актуальное «Осталось: ≈ N» в KPI и в сайдбаре.
- Оценка честная: считаются **все** незаконченные задачи (включая ожидающие
  очереди и сбойные — их же можно повторить), из веса вычитается уже скачанное,
  для задач с неизвестным весом берётся средний вес скачанного этого фильма,
  потом общий средний, потом заглушка 1.5 ГБ. Субтитры по заглушке не
  оцениваются — они «весят» килобайты, и «1.5 ГБ за субтитры» было бы ложью.
- Место считается по той папке, куда файлы **реально** пишутся (медиатека, если
  настроена, иначе папка загрузок) — раньше цифра могла относиться к другому
  диску.

### Кто-то добавил задачу вручную

В веб-морде есть форма «Добавить по ссылке» — для случая, когда прямая ссылка
уже есть на руках. Без метаданных сервер возьмёт имя из самой ссылки
(`filenameFromUrl`) и положит в корень папки загрузок.

### Прямая ссылка без расширения вообще

`curl -X POST http://сервер:8080/api/tasks -H 'Content-Type: application/json' -d
'{"url":"https://…/file.mp4"}'` — API полностью открыт и задокументирован в
[`server.md`](server.md#api).

## 4. Почему так, а не иначе — принятые решения

Короткий список «почему не X»:

- **Почему сервер не парсит сайт сам?** Сайт отдаёт серверу страницу входа /
  «проверяем, что вы не бот». Сессия есть только у вашего браузера. Поэтому
  резолв — на клиенте. (Теоретическое решение — FlareSolverr/куки — в TODO.)
- **Почему расширение запрашивает ссылки из страницы, а не из service worker?**
  Из страницы запрос несёт куки/Referer автоматически и проходит Cloudflare;
  из service worker пришлось бы подменять заголовки DNR-правилами и городить
  фолбэк «через страницу» — так и было сделано в старом расширении, но это
  сложнее и ломучее.
- **Почему проба качества на клиенте, а не на сервере?** Проба должна идти с
  `Referer` страницы и не желает ходить с сервера к CDN без необходимости.
  Плюс клиенту нужно показать вес **до** отправки — для предупреждения о месте.
- **Почему Node без зависимостей?** Один бинарный запуск, NixOS-пакет из
  `nodejs + обёртка`, ничего не ломается при обновлениях. Единственная внешняя
  программа — `ffmpeg`, и то опционально (только для HLS).
- **Почему имя файла собирает сервер, а не расширение?** Шаблоны меняются в
  веб-морде и применяются ко всем клиентам; клиент не должен знать раскладку
  медиатеки. (Клиент может передать `filename` сам — API разрешает, но
  расширение этим не пользуется.)
- **Почему опрос, а не WebSocket?** При самолимите «до сотни задач» опрос
  раз в секунду дешевле в поддержке и не требует WS-инфраструктуры. В TODO —
  SSE/WS, если задач станет заметно больше.

Дальше — по деталям: [`server.md`](server.md) и [`extension.md`](extension.md).
